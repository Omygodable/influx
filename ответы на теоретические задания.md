1) Минимальный набор метрик для платформы вычислений (http, отчёты на диск, загрузка CPU):

    cpu_usage (загрузка CPU – важно для вычислительной нагрузки)

    http_requests_total (общее число запросов)

    http_request_duration_seconds (латенция ответов)

    disk_usage_bytes / disk_free_bytes (сохранение отчётов)

    http_responses_count_by_code (распределение ответов)

    Обоснование: мониторить утилизацию CPU, доступное место на диске, доступность и производительность HTTP.

2) Что предложить менеджеру вместо RAM/inodes/CPUla:

    Ввести SLO (Service Level Objectives) на основе доступности и качества обслуживания, например:
    *Доля успешных HTTP-запросов (2xx) ≥ 99.5% за месяц*
    *Время отклика (95-й перцентиль) ≤ 200 мс*
    Доступность платформы (Uptime) ≥ 99.9%

    Показывать дашборды с процентом выполнения SLA по каждому клиенту/отчёту.

3) Как собирать ошибки без финансирования на логи:

    Встроить в приложение отправку ошибок через syslog или stdout/stderr, а затем использовать бесплатные решения:
    Docker-драйвер для логов (json-file) + бесплатный сборщик вроде Loki (с ограничением по объёму)
    Настроить Telegraf для сбора логов из файлов и отправки в InfluxDB (как временное решение)
    Использовать самописный скрипт для ротации и отправки критических ошибок по почте/в Telegram

    (Вариант) Применить ELK в минимальной конфигурации (один экземпляр без репликации) – но это не бесплатно по ресурсам.

4) Почему SLA=70% при отсутствии 4xx и 5xx:

    Ошибка в формуле: summ_2xx_requests / summ_all_requests.

    Если нет 4xx и 5xx, но и 2xx мало, значит есть 3xx (редиректы) и, возможно, 1xx.

    Решение: учитывать только успешные ответы (2xx), а в знаменателе брать все ответы, кроме явно исключённых по SLA (например, не считать 3xx, если редиректы нормальны). Или переопределить SLA как долю запросов, не приведших к ошибке (2xx + 3xx) / все ответы.

5) Плюсы и минусы pull/push систем:

    Pull (Prometheus):
    Плюсы: легко обнаруживать недоступные цели, встроенная аутентификация, контроль частоты опроса, отсутствие проблем с перегрузкой агентов.
    Минусы: сложно получать метрики из-за NAT/firewall, нужна Service Discovery, высокое потребление ресурсов на центральном сервере при тысячах целей.

    Push (InfluxDB с Telegraf, Graphite):
    Плюсы: проще отправлять метрики из краткосрочных задач (батчи, cron), нет проблем с NAT, легче балансировать нагрузку.
    Минусы: нельзя гарантировать доставку, сложнее обеспечивать надёжность и контроль версий данных, возможен перегруз канала.

6) Классификация систем:

    Prometheus – pull (с поддержкой push через Pushgateway)

    TICK – push (Telegraf отправляет в InfluxDB)

    Zabbix – гибрид (активные и пассивные проверки, агенты могут сами пушить)

    VictoriaMetrics – push (совместима с InfluxDB line protocol, но можно и pull по Prometheus)

    Nagios – pull (активные проверки с сервера)
